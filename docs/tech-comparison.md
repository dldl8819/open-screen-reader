# 기술 스택 비교 (초안)

MVP(Windows 10/11, 포커스 추적 + 음성 출력 + 기본 리뷰)를 만드는 데 쓸 언어와 구조를 비교합니다.
아래 평가는 일반적인 특성에 근거한 것이며, 프로토타입에서 실제로 측정한 뒤 결정합니다.

## 1. 공통으로 필요한 구성요소

| 구성요소 | 역할 |
| --- | --- |
| 접근성 수집기 | UI Automation, MSAA/IAccessible2 등으로 포커스와 요소 정보를 얻습니다. |
| 입력 후킹 | 전역 단축키와 키 입력을 가로채 화면 읽기 프로그램 명령으로 처리합니다. |
| 리뷰 모델 | 현재 창 내용을 개체/줄/단어/글자 단위로 탐색할 수 있는 구조입니다. |
| 음성 엔진 | SAPI 5, Windows OneCore 등 TTS를 호출하고, 대기열과 즉시 중단을 관리합니다. |
| 설정 UI | 키보드만으로 조작 가능한 설정 화면입니다. |

## 2. 후보 비교

| 항목 | C# / .NET | Rust | C++ |
| --- | --- | --- | --- |
| Windows 접근성 API 연동 | 쉬움. UI Automation 클라이언트 라이브러리가 있어 시작이 빠릅니다. | 가능. `windows` 크레이트로 UIA COM을 호출하나 코드량이 많습니다. | 가능. UIA/MSAA를 가장 직접적으로 사용합니다. |
| 개발 속도 | 빠름 | 보통 (학습 곡선 있음) | 느림 |
| 메모리 안전성 / 안정성 | 보통. 메모리 관리는 안전하나 GC 지연이 있을 수 있습니다. | 높음. 컴파일 단계에서 많은 오류를 막습니다. | 낮음. 직접 관리해야 합니다. |
| 실행 지연 | 보통. 시작 시간과 GC가 영향을 줄 수 있어 측정이 필요합니다. | 낮음 | 낮음 |
| 크로스플랫폼 코어 재사용 | 제한적 (macOS는 별도 구현 필요) | 좋음. 코어를 공유하고 플랫폼 어댑터만 분리하기 쉽습니다. | 좋음 |
| 설치/배포 | .NET 런타임 필요 (자체 포함 배포 가능) | 단일 실행 파일로 만들기 쉬움 | 런타임 부담 적음 |
| 개발자 확보 | 쉬움 | 보통 | 보통 |

참고로 대표적인 오픈소스 화면 읽기 프로그램인 NVDA는 Python과 C++를 함께 쓰는 구조입니다. 로직은 스크립트 언어로, 성능이나 시스템 연동이 중요한 부분은 네이티브로 나누는 방식입니다.

## 3. 아키텍처 후보

### A안. 단일 언어(C#) 모놀리식
- 장점: 가장 빨리 프로토타입을 만들 수 있습니다.
- 단점: macOS 확장 시 코어를 다시 써야 할 가능성이 큽니다.

### B안. 공통 코어(Rust) + 플랫폼 어댑터
- Windows 어댑터(UIA), macOS 어댑터(AXUIElement, Swift 연동 필요)가 코어와 통신합니다.
- 장점: 장기적으로 코드 재사용과 안정성이 좋습니다.
- 단점: 초기 비용이 큽니다.

### C안. 하이브리드
- 프로토타입은 C#으로 빠르게 만들어 지연과 접근성 API 동작을 검증합니다.
- 결과에 따라 지연이 민감한 부분(음성 대기열, 입력 처리)만 네이티브로 옮기거나, 코어를 Rust로 재작성합니다.

## 4. 임시 권고

**C안(하이브리드)으로 시작해 Windows 프로토타입을 C#으로 만들고 지연을 측정한 뒤 본 구현의 언어를 확정하는 것**을 제안합니다. 이유는 다음과 같습니다.

- 가장 큰 불확실성은 "접근성 API로 원하는 정보를 안정적으로 얻을 수 있는가"와 "음성 지연이 충분히 작은가"입니다.
- 이 두 가지는 언어 선택보다 프로토타입으로 확인하는 것이 확실합니다.
- 프로토타입의 코드는 버려도 되는 코드로 취급하고, 얻은 지식을 설계 문서에 남깁니다.

## 5. 프로토타입 검증 항목

| 번호 | 검증 내용 | 성공 기준(초안) |
| --- | --- | --- |
| P1 | UI Automation으로 포커스 변경 이벤트를 받아 요소의 이름과 역할 읽기 | 메모장, 탐색기, 크롬에서 동작 |

| P5 | 전역 단축키로 음성 중단 | 어떤 앱에서도 동작 |
| P6 | 장시간 실행 시 메모리와 CPU 사용량 | 증가 추세 없음 |
